HELP: how a search works and what each column means

      
    

    

      
How a search works

      
Flow records come from monitor/flows, which keeps 90 days of history and returns one hour per
        request, up to 1,000 flows per page. So a search is a job on the server that reads its range hour by hour, newest first, for
        every site at once, and the table fills in as pages arrive. The API answers about 2 pages every 8–10 s and allows 2 requests at
        a time per tenant (shared by every tab), so the only way to make a search faster is to read less:

      
    
        
  • Filters (IP, destination ports, protocol, applications) are applied by the API, so fewer flows are fetched.
          Searches over 4 hours need an application or IP filter.
    • 
        
  • Saved hours: an hour that ended over an hour ago, once read in full, is saved in
          data/flowcache.db (up to 500 MB) and reused by any later search of the same site with the same filters.
    • 
      

      
A search pauses every 200,000 flows (every flow is kept in this tab): Keep going or Stop here. Stop
        keeps what has loaded. A flow open across hours is reported in each, and merged into one row. If one hour fails, the rest of
        the site's flows still show, with a warning naming the hour. View API query shows the request sent.

      
What each column means

      
Each row is one flow record from the ION: one connection (TCP) or conversation (UDP, ICMP) between a client and a server,
        reported when it ends or as it ages out. C2S = client to server, S2C = server to client; the
        client is whoever started the flow. Hover a column heading for a short version, a cell for per-direction values. Add a group of
        columns with its + button under Add columns: the button then sits over its columns, and clicking it there
        (✕) removes them again. Columns turns single columns on and off; - means not reported or doesn't apply.

      
Who and where

      

        
Site
The site whose ION recorded the flow.

        
Time
When the flow started, in your browser's time zone.

        
Source IP / Src Port
The client: the device that opened the flow, and its (usually random) port.

        
User
The user signed in on the source IP, when user identification is set up (e.g. domain\user).

        
Dest IP / Dst Port
The server and the service port (443 HTTPS, 53 DNS, 389 LDAP…).

        
Proto
IP protocol: TCP, UDP, ICMP or another number.

        
App
The application the ION identified (Prisma SD-WAN app definitions, including custom apps).

        
Domain
The domain name seen for the flow (from DNS or the TLS server name), e.g. chatgpt.com.

        
Direction
Which way the flow crossed the ION, e.g. LAN to WAN (branch user out), WAN to LAN (into the site), LAN to LAN.

      

      
Policy and path

      

        
Path Policy
The path (network) policy rule that matched: decides which WAN paths the app may use.

        
QoS Policy
The priority (QoS) policy rule that matched: decides the traffic class and queue.

        
Security Policy
The security (zone firewall) policy rule that matched.

        
Path
The WAN path the flow used, e.g. Direct Internet (ISP name) or a VPN to a data center or hub, shown as
          local circuit → remote site (remote circuit).

        
Path Change
Why the flow moved to another path mid-way (e.g. SLA breach, path down, asymmetry). Blank: it stayed on
          one path. Underneath, from … is the path it was on before, when the search goes back far enough to include it (hover
          for every path with times). Path shows where the flow was at the end of the searched range.

        
Assurance
Flow Move when a performance policy rule with the Move Flows action put the flow on its
          path, e.g. because another path broke the rule's SLA (SCM's Assurance: Flow Move). Underneath, from … is
          the path it was kept off and why (e.g. app RTT: the app's round-trip time on that path was over the SLA); hover for
          every path it was kept off. When the flow moved mid-way (Path Change then says why, e.g. probe_bad_path_change)
          that's the path it was on before; when it was placed on its path at the start, it's the path flows normally take. The
          Flow moved button shows only these flows.

      

      
Performance (AppStats)

      

        
Avg RTT
Network round-trip time, measured by the ION from the TCP handshake and ACKs. High = slow or distant path.

        
Avg SRT
Server response time: from a request to the server's first reply. High SRT with normal RTT = a slow server or
          app, not the network.

        
Avg UDP TRT
UDP transaction response time: request to reply for UDP apps (e.g. DNS).

      

      
Volume (TotalFlowStats, DirectionalFlowStats)

      

        
Bytes / Packets C2S, S2C
Data sent each way. Downloads are mostly S2C, uploads C2S.

        
Total Bytes / Packets
Both directions added up.

        
Duration
Flow end minus start. Long flows with little data are usually idle connections kept open (web apps, chat,
          LDAP, SMB). (open): still open at the end of the searched range, so this is how long it had been open.

        
Within the searched range
Bytes, packets and retransmits count only traffic inside the searched range: a flow that
          started earlier, or is still open, carried more in total.

      

      
Retransmits (TCP)

      

        
Retx Pkts
TCP packets the ION saw sent a second time. Usually a sign of packet loss or congestion, which TCP recovers
          from: users see slowness, not failure. "keepalive" marks 1-byte keepalive probes: on an idle connection the
          client (browsers every ~45 s) resends one byte the server already acknowledged, so the ION counts it as a retransmit even when
          it's answered. When a direction's Retx Bytes equals its Retx Pkts, every one was a 1-byte probe, not lost data. Those are left
          out of Retx % and of sorting.

        
Retx %
Real retransmits as a share of all the flow's packets. Under ~1% is normal; a few % and up on many flows of one
          path or direction points to loss there.

        
Retx Bytes
Data retransmitted. Real loss shows full-size segments (~1,300 bytes per packet); 1 byte per packet is probes.

      

      
Retransmits are per flow and network-level. They differ from Site details' failed transactions, an application-level
        count per app (an exchange that didn't complete, for any reason). Heavy retransmits can cause failed transactions; clean flows
        with failures point to the server or app.

      
Voice / video

      

        
Jitter
Variation in packet delay, worse direction. Above ~30 ms hurts calls.

        
Loss
Media packets lost, worse direction. Above ~1% is audible.

        
MOS
Estimated call quality, 1 (bad) to 5 (excellent); 4+ is good. Only for media the ION can read: encrypted media
          such as Teams shows -.

      

      
Outcome

      

        
Action
What the ION did: forwarded, or flow_drop. Dropped flows show why underneath (TCP state violation,
          security deny, no allowed path up…); hover for details.

        
End Reason
How the session ended: tcp-fin (normal close), tcp-rst-from-client /
          -server (reset), aged-out (idle timeout). n/a: not reported by this ION's software (before
          6.8).

        
Init OK (Init Success)
Whether the ION saw the TCP connection set up (the 3-way handshake) complete.
          Yes: it completed. No: it did not (no answer, a refusal, or a half-finished handshake).
          -: doesn't apply (UDP, ICMP).

        
Return (Return Traffic)
What came back from the server, from the packet counts and TCP flags in the record.
          Yes: the server sent data back. Reset: the only reply was a TCP reset (nothing listens on
          that port, or a host firewall rejected it). SYN-ACK only: the server accepted, but the client never sent the
          final ACK (it gave up, or its ACK took a path the ION didn't see). No: forwarded, but nothing came back.
          Dropped: the ION dropped the flow itself (the Action column says why), kept apart from No.
          -: no packets in either direction.

        
Security
The security policy action(s) applied, e.g. allow, deny.

      

      
Reading Init OK and Return together when Init OK is No: Return = No means
        nothing answered (often the SYN was sent several times): look at the network path (routing, a firewall or policy drop, or the
        host is down). Reset or SYN-ACK only: the server is reachable but refused or the handshake
        stalled: look at the service or port, not the path.

      
Tip: many failed connections from one source to many ports or hosts (e.g. 80, 135, 445, 9100) is usually a
        network scanner or monitoring tool probing for open services, not a user-facing problem. Filter the Source IP column to check.

      
Init failed and No return traffic filter the table to Init OK = No and Return = No; an active one shows ✓ … ✕: click it again to remove it.
        No return traffic leaves out dropped flows; pick Dropped in the Return column filter to see those.
